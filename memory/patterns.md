# Patterns

## Session restarts

- Crons (`/loop` for Slack check 1m, heartbeat 30m) are **session-only** — they do not survive a session restart. Every new session must recreate them from `config.json` at startup, per the bootstrap procedure in CLAUDE.md. (source: sessions 2026-08-23, 2026-08-24, confidence: high)
- The agent restarts very frequently (many sessions per day, sometimes minutes apart — 14 session files logged between 2026-08-22 and 2026-08-24). Each restart re-reads all bootstrap files and re-sends a Slack "back online" notification to `#asistent-nic`. This is expected behavior from the Windows Task Scheduler + Git Bash restart-loop persistence design (see CLAUDE.md "Persistence"), not a malfunction — but it means Slack gets a fresh online-notification often. (source: session file listing 2026-08-22..24, confidence: high)

## Known bug (fixed)

- [2026-08-23] `check-slack.sh` and `send-slack.sh` failed with `ERROR: SLACK_BOT_TOKEN not set` when run directly by cron, because they didn't source `.env` themselves. Fixed by adding an explicit `.env` source at the top of both scripts. Commit `ed70d19 fix: sourceaza .env explicit in check-slack.sh si send-slack.sh`. Verified working since — first Slack send of 2026-08-24 session succeeded without manual `source .env`. (source: session 2026-08-23, commit ed70d19, confidence: high)
- [2026-08-24] `agent-start-windows.sh` checked whether `claude.exe` had started only 10s after launch, but real bootstrap (reading IDENTITY/SOUL/CONTRACT + `/loop` per cron) takes 2-5 minutes — so `is_agent_running()` didn't find the process yet, treated it as a crash, and relaunched the WT window; after 3 such false positives (~90s) the supervisor HALTed even though the agent was starting up normally. Reproduced and confirmed in production on 2026-08-23/24 (`crashes.log`). Fixed with a 5-minute grace period after each (re)launch before crash-checking begins (crash counter only increments after the grace period expires), plus a retry in `launch-agent-window.ps1` for when `wt.exe` doesn't attach a visible window on the first attempt (WindowsTerminal.exe server not yet "warm"). Tested end-to-end via a real Task Scheduler run: full bootstrap → crons set → Slack "back online" sent, no crash/HALT in activity.log/crashes.log. Commit `e25e6f0 fix: elimina fals-pozitive de crash la auto-start pe Windows`. (source: commit e25e6f0, confidence: high)
- [2026-08-25] Diacritics (ă î ș ț â) and em-dashes rendered as "?" in Slack messages sent by the agent. Root cause was NOT jq (produces correct UTF-8) but `curl.exe` — a native Windows binary — corrupting non-ASCII argv when MSYS bash passes it via `--data "$(...)"`. Fixed in `send-slack.sh` by writing the JSON payload to a temp file and sending with `curl --data-binary @file` instead of `--data` as an inline argument; same fix applied to `notify.sh` and the crash-alert path in `agent-start-windows.sh` (both had the identical `--data "$(jq ...)"` pattern). Verified end-to-end for `send-slack.sh` (message with diacritics + em-dash read back correctly from Slack `conversations.history`); the `notify.sh`/crash-alert copies are untested live but use the identical verified pattern. `check-slack.sh` never had this bug (uses `--data-urlencode` with ASCII values only, no argv text passing). Commit `7fea14e feat: portare health/watchdog pe Windows, fix diacritice, raport zilnic`. (source: session 2026-08-25, commit 7fea14e, confidence: high)

## Parallel agent sessions

- [2026-08-25] Multiple agent sessions can run concurrently (e.g. across Task Scheduler restarts or separate windows) and commit — or edit memory files — independently. Observed twice: (1) a parallel session committed `3d38af3` (security/anti-prompt-injection work) while the current session was mid-conversation about the same pending change; (2) a concurrent write collided with this file (`memory/patterns.md`) during dream consolidation on 2026-09-03, temporarily producing duplicate entries that had to be merged by hand. Always check `git status`/`git log` before assuming what still needs to be committed, and re-read a memory file immediately before editing if another session might be active. (source: sessions 2026-08-25, 2026-09-03, confidence: high)
- [2026-09-03] (Corrected — previously undercounted as "7 times") Concrete instance of the above, and NOT a one-off: counting `aiTitle:"Dream memory consolidation skill"` sessions directly from the transcript files shows **two** separate runaway bursts, on two different days — **18 invocations on 2026-08-24** (19:45:51–19:57:14 UTC, ~11.5 minutes, several pairs seconds apart) and **17+ invocations on 2026-09-03** (08:50:34–09:00:08 UTC, ~9.5 minutes, same tight-pairs pattern — including a sub-burst of ~15 session files in the 11:53–11:58 local window alone, `.last-dream` landing at 11:57:40 mid-burst), each running its own ORIENT→GATHER→CONSOLIDATE→PRUNE pass over the same `MEMORY.md`/`memory/*.md` files concurrently — effectively several dream runs per minute at peak, not per day. Both bursts converged without a git conflict, but that's luck, not design — nothing prevents two dream runs from clobbering each other's edits mid-flight, and the true scale (35+ dream sessions total logged for this project as of 2026-09-03) is much larger than the "7" first recorded, and at this frequency the "no conflict yet" luck is running thin. Root cause unchanged: dream's auto-trigger (global Stop hook + `~/.claude/skills/dream/should-dream.sh` + `.dream-config`) is **not installed** on this machine (confirmed: `~/.claude/skills/dream/` doesn't exist, no `dream` entry in `~/.claude/settings.json` Stop hooks) — see [[facts]]. Every one of these runs was a manual/external invocation with no cheap guard against re-firing while a prior run is still in flight, and this has now recurred on two separate days, so it is a standing risk, not an isolated incident. **Action still pending, now higher priority:** actually add a lock file (e.g. `.dream-running`) checked at the top of Phase 1 that aborts (or waits) if another dream is already active — next time dream code is touched, not just noted as a suggestion. (source: direct count of `aiTitle` + timestamp fields across session transcripts, 2026-09-03, confidence: high)
- [2026-09-03] `.last-dream` location was inconsistent across recent runs: some sessions wrote it to the project root (`.last-dream`, the canonical location per `should-dream.sh`'s `project-root` case — reads `$DREAM_MEMORY_PATH/.last-dream`), others wrote a second copy to `memory/.last-dream` (the `native`-type convention from the SKILL.md template, wrongly applied here). Both paths are gitignored (`.gitignore:9`), so this never surfaced as a commit conflict, only as confusing state when checking "how long since last dream". Canonical for this project is root `.last-dream` — the stray `memory/.last-dream` was removed 2026-09-03 to avoid future confusion. (source: direct inspection of should-dream.sh + both files, confidence: high)

- [2026-09-03, consolidated — 6 confirming runs, 12:00-12:09] Between 12:00 and 12:09 the same self-referential burst was independently reconfirmed 6 times (12:00, then four "blocked attempt" runs at ~12:02-12:08, then this run at 12:09): each time, 5-28 new session files had appeared in the preceding minutes, sampled files were content-checked and were 100% `aiTitle:"Dream memory consolidation skill"` self-invocations with zero user/Slack signal, and each run attempted the same `Step -1` `.dream-running`-lock edit to `.claude/skills/dream/SKILL.md` and was **blocked by an identical permission prompt every single time (4-for-4 on that specific edit)** — confirming the block is systematic (scoped to that file/path), not a fluke. **Decision: stop attempting the SKILL.md edit and stop logging further "still blocked" entries** — this needs direct human action (grant edit permission on `.claude/skills/dream/SKILL.md`, or apply the `Step -1` snippet by hand: insert a "Step -1: Claim the lock" subsection — claim `.dream-running` at start with a 600s staleness window, release at end of Phase 4 — immediately before "### Step 0: Read config" under "## Phase 1: ORIENT"). (source: sessions 2026-09-03 12:00-12:09, confidence: high)
